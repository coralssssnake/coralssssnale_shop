Схема «звезда» состоит из двух фактов и трех измерений:

1. Факт `fct_orders` связан с измерением `dim_customers` по ключу `customer_id` и с `dim_dates` по ключу `order_date`.

2. Факт `fct_order_items` связан с `fct_orders` по ключу `order_id`, с `dim_products` по ключу `product_id` и с `dim_dates` по ключу `order_date`.

3. Измерение `dim_customers` содержит атрибуты клиента и флаг `is_buyer`.

4. Измерение `dim_products` содержит иерархию категорий.

5. Измерение `dim_dates` содержит календарь.

**Зернистость и бизнес-вопросы**

1. Витрина fct_orders имеет зернистость «заказ» и отвечает на вопросы о выручке по месяцам, категориям и среднем чеке по городам.

2. Витрина fct_order_items имеет зернистость «товар в заказе» и отвечает на вопрос какие бренды и товары чаще возвращают.

3. Витрина dim_customers имеет зернистость «клиент» и хранит долю покупателей по каналам привлечения.

4. Витрина dim_products имеет зернистость «товар» и используется для срезов по иерархии категорий.

5. Витрина dim_dates имеет зернистость «день» и используется для календарных срезов.

**Хранение в Greenplum**

1. Для витрины fct_orders выбран тип table, колоночное хранение и распределение по ключу order_id. Это крупный факт, и распределение по order_id совпадает с сырой таблицей raw.orders.

2. Для витрины fct_order_items выбран тип incremental, колоночное хранение и распределение по order_id. Эта витрина джойнится с fct_orders по order_id, соу если бы мы распределили её по product_id, Greenplum при каждом соединении с fct_orders был бы вынужден перемешивать данные между сегментами, а это привело бы к огромным задержкам. Распределение по order_id позволяет делать JOIN локально на каждом сегменте.

3. Для измерений dim_customers, dim_products и dim_dates выбрана table и репликация на все сегменты. Это мини справочники, и их полная копия на каждом сегменте позволяет выполнять JOIN с фактами без пересылки строк по сети.

4. Ключи распределения фактов совпадают с ключами сырых таблиц, что обеспечивает локальную обработку запросов. Если бы ключи фактов различались, Greenplum не смог бы выполнить JOIN локально, и данные пришлось бы в моменте перераспределять между сегментами, а это больно ударит по производительности.
